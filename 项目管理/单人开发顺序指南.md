# 单人开发顺序指南

> 核心原则：**永远有东西在跑。** 每一步结束都产出可点击、可观看、可给人试玩的可见成果。

---

## 为什么不用实现路线图里的"三阶段"顺序？

[[实现路线图]] 把任务分成了"内容创作 → 技术实现 → 测试打磨"三个阶段。这对团队合理——写剧本的和写代码的可以并行。但一个人这样做会出问题：

```
❌ 单人照搬三阶段的后果：
   花两个月写完全部剧本 → 一行代码没写
   → 不知道剧本在引擎里读起来什么感觉
   → 不知道分支逻辑有没有死路
   → 看不到任何可运行的东西 → 动力枯竭
```

正确做法：**以"可运行"为节奏，内容与技术交替推进。**

## 里程碑 1：第一段文字出现在屏幕上

**目标**：把节点日1的剧本变成浏览器里能逐句点击阅读的东西。线性即可，不需要选择。

**为什么这是第一步**：哪怕只有一个文本显示，你已经有了"游戏"的雏形。后续所有工作都是在这个骨架上加东西。

### 1.1 写一份极小的剧本文件

先不写完整剧本——只写节点日1的前 30-40 行。够你看到对话节奏就够了。

格式自定，建议 JSON（最易解析）：

```json
[
  { "type": "narration", "text": "快递盒比想象中轻。" },
  { "type": "narration", "text": "你拆开灰色的包装，里面是一台巴掌大的设备。屏幕暗着，外壳是某种摸起来不像塑料的材料。" },
  { "type": "dialogue", "speaker": "旁白", "text": "按照说明书，你按住侧面的电源键。" },
  { "type": "narration", "text": "屏幕亮了起来。" },
  { "type": "dialogue", "speaker": "RC-Edu-7", "text": "你好。我是 RC-Edu-7。请告诉我你的学习目标。" }
]
```

**产出**：`scripts/node-day-01.json`（30-40行即可）

### 1.2 搭一个 HTML 页面显示它

一个文件，包含：
- 一个背景区域（先用纯色 `#1a1a2e` 占位）
- 一个底部文本框
- 点击推进到下一行
- 文字逐字出现（typewriter 效果——加分项，非必须，但做起来其实只要 10 行代码，体验提升很大）

```
需要写的代码量：约 100-150 行 HTML+CSS+JS
预计耗时：一个下午
```

**产出**：`index.html` ——双击打开，点击屏幕，文字逐行出现。

### 1.3 读完整个节点日1

把你写好的 30-40 行从头到尾点击一遍。感受：
- 节奏对不对？
- 哪些句子太长/太短？
- 对话的自然度如何？

回头改剧本文件，刷新页面，再看。**这就是"随时可见"的意义——你立刻知道剧本在引擎里的感觉。**

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑1完成 | 双击 index.html，能从头到尾读完节点日1的线性剧本 |

## 里程碑 2：玩家能选择，剧情能分支

**目标**：加入选择系统。玩家点击选项后走向不同的对话。

### 2.1 在脚本格式中加入选择和标签

```json
{ "type": "choice", "choices": [
    { "text": "我想学好数学。", "target": "math_path" },
    { "text": "我其实……不太确定自己想要什么。", "target": "uncertain_path" }
] },
{ "type": "jump", "target": "after_choice" },

{ "type": "label", "id": "math_path" },
{ "type": "dialogue", "speaker": "RC-Edu-7", "text": "明白。数学是需要系统性规划的学科。我们先做一次诊断测试？" },
{ "type": "jump", "target": "after_choice" },

{ "type": "label", "id": "uncertain_path" },
{ "type": "dialogue", "speaker": "RC-Edu-7", "text": "……" },
{ "type": "dialogue", "speaker": "RC-Edu-7", "text": "这也是一种起点。不确定意味着你没有预设答案。这在学习中是有价值的。" },
{ "type": "jump", "target": "after_choice" },

{ "type": "label", "id": "after_choice" },
{ "type": "narration", "text": "窗外有车经过，光柱扫过天花板，又消失了。" }
```

### 2.2 改造引擎

在 1.2 的代码基础上加入：
- `choice` 类型的处理——显示选项按钮
- `jump` 类型的处理——跳转到对应 label
- `label` 类型的处理——标记脚本位置（运行时建一个 `label → index` 的索引表）

```
新增代码量：约 80-120 行
预计耗时：一个下午到一个晚上
```

### 2.3 在节点日1剧本中插入 2-3 个选择点

不用多——2到3个选择，每个2个选项。先感受分支的节奏。

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑2完成 | 能从头玩到尾，不同选择看到不同对话，不会卡死 |

## 里程碑 3：选择有后果——变量与条件

**目标**：玩家的选择不只是即时分叉，还会累积影响后续内容。

### 3.1 扩展脚本指令

```
[设置 trust +1]          → { "type": "set_var", "key": "trust", "op": "+", "value": 1 }
[标记 first_night_talk]  → { "type": "set_flag", "key": "first_night_talk" }
[如果 trust >= 5 跳转 xx] → { "type": "if", "condition": {...}, "target": "xx" }
```

### 3.2 实现 VariableStore

参考 [[传统文字恋爱游戏实现指南#六变量与-flag-系统]] 中的实现——核心是一个 `Map<string, number>` 和一个 `Map<string, boolean>`，加上序列化/反序列化。

```
新增代码量：约 100-150 行
预计耗时：一个晚上
```

### 3.3 在剧本中埋变量

把节点日1的脚本加入变量操作：
- 选择"说出真实困惑" → `trust +1`
- 选择"只说学习目标" → `trust` 不变
- 深夜对话 → `flag: first_night_talk`

然后在节点日1结尾加入一个条件分支：如果 `trust >= 2`，机器人的道晚安方式略有不同。

**这很关键**——你会在这一瞬间看到"我的选择改变了后续"的效果。这是文字恋爱游戏最核心的魅力。

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑3完成 | 不同选择累积不同变量值，结尾的条件分支能正确触发 |

---

## 里程碑 4：存档 & 完整游戏循环

**目标**：玩家能存档/读档，有主菜单，构成一个完整的"打开→游玩→存档→退出→读档→继续"闭环。

之前三个里程碑你能"看完"游戏，但留不住进度。现在把它变成一个真正的 **可持久化应用**。

### 4.1 存档数据结构

参考 [[传统文字恋爱游戏实现指南#八存档系统]] 的 SaveData 定义。核心字段：
- 当前脚本位置（label + index）
- 所有变量和 flag
- 对话历史（用于回看）
- 时间戳 + 章节名（用于存档列表显示）

### 4.2 存档槽

先做最简版：
- 5 个手动存档槽
- 1 个自动存档（关键节点前自动保存）
- 存储到 `localStorage`（如果改 Electron，后续迁移到文件系统也很方便——接口一样）

### 4.3 主菜单

```
┌──────────────────────────┐
│        RC-Edu-7          │
│                          │
│   [  新游戏  ]           │
│   [  继续游戏 ]          │
│   [  读取存档 ]          │
│   [  设置    ]           │
└──────────────────────────┘
```

### 4.4 游戏内暂停菜单

按 ESC 弹出：返回 / 存档 / 读档 / 设置 / 返回标题

### 4.5 设置面板（先做最少的）

- 文字显示速度（快/中/慢——控制 typewriter 的 ms/字）
- 音量滑块（先放着，还没音频）

```
新增代码量：约 300-500 行（存档逻辑+UI+菜单）
预计耗时：2-3 个晚上
```

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑4完成 | 完整的"打开→新游戏→玩→存档→退出→读档→继续→玩到结局"闭环可用 |

## 里程碑 5：视觉层——背景 + 角色立绘

**目标**：把纯色背景和纯文字，升级为有背景图和角色立绘的视觉体验。

### 5.1 先占位，后替换

**不要等正式美术**。先自己用：
- 背景：找免费照片/自己拍/纯色渐变 → 调到合适氛围
- 立绘：简单几何图形/剪影 → 占好位置和大小

这样代码写好后，美术素材出来直接替换文件即可。

### 5.2 背景管理系统

- 加载背景图
- 切换背景（至少支持 fade 过渡）
- 背景图按场景 ID 索引

### 5.3 角色立绘系统

- 按角色 ID + 表情 ID 加载立绘
- 显示/隐藏（带动画：fade/slide）
- 位置：左/中/右（屏幕比例定位）
- 多个角色同时在场

### 5.4 脚本扩展

```
[背景 dorm_night]
[显示 robot_rc7 右 默认]
[表情 robot_rc7 thinking]
[隐藏 robot_rc7]
```

### 5.5 先做一个场景的完整视觉

只做节点日1的"宿舍夜晚"场景。背景占位 + RC 剪影立绘 + 两个表情（默认/思考）。跑通整个节点日1。

**这一个场景的视觉效果出来后，你会第一次感觉"这是个真正的游戏"**——这是整个开发过程中士气提升最大的一步。

```
新增代码量：约 200-300 行
预计耗时：3-5 个晚上（含占位素材制作）
```

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑5完成 | 节点日1在视觉上完整——有背景、有立绘、有表情切换、有过渡效果 |

## 里程碑 6：全部内容写进引擎

**目标**：8 个节点日的完整剧本 + 所有结局路线都可到达。

这是最耗时的里程碑——写内容是实打实的时间投入。但好消息是**引擎已经完成了**，你只需要写剧本文件。

### 6.1 写剧本的策略（非常重要）

**不要从头写到尾。** 按"可测"的粒度切分：

```
节点日1 的完整剧本（含 3-4 个选择点）  → 写完 → 跑通 → 调整
节点日1→2 的过渡文本                   → 写完 → 跑通
节点日2 的完整剧本                      → 写完 → 跑通
节点日2→3 的过渡文本                   → 写完 → 跑通
……
```

每写完一个节点日就跑一遍，确保：
- 没有死路（所有选择都能走出对话）
- 变量操作正确（用开发者面板显示当前变量值）
- 条件分支触发正确

### 6.2 加一个开发者面板

在做内容生产阶段，强烈建议在页面上加一个隐藏/小型的开发者面板：

```
┌──────────────────┐
│ trust: 3         │
│ closeness: 1     │
│ deep_talk: 0     │
│ first_night: true│
│ [跳转到节点日3]   │
│ [重置所有变量]    │
└──────────────────┘
```

按 ` 键（反引号）呼出/隐藏。**这个东西能节省你无数时间**——不用从头玩才能测后面的分支。

### 6.3 结局配置

每个结局的触发条件用数据定义，不硬编码：

```json
{
  "endings": [
    {
      "id": "ending_truth",
      "name": "真结局·那条缝隙",
      "conditions": [
        { "key": "trust", "op": ">=", "value": 8 },
        { "key": "unexpected_triggered", "op": "==", "value": true }
      ],
      "scriptLabel": "ending_truth_start"
    },
    {
      "id": "ending_normal",
      "name": "普通结局·毕业",
      "conditions": [
        { "key": "trust", "op": ">=", "value": 4 }
      ],
      "scriptLabel": "ending_normal_start"
    }
  ]
}
```

结局判定在最后节点日自动执行——按优先级依次检查条件，第一个满足的触发。

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑6完成 | 8个节点日全部可玩，所有结局可到达，无死路，变量系统正确 |

## 里程碑 7：音频 + UI 润色

**目标**：加 BGM 和音效，UI 从"功能可用"升级到"有设计感"。

### 7.1 音频

先做最少的：
- 3-5 条 BGM（日常/温馨/紧张/悲伤/结局）
- 3-5 个音效（系统启动声、敲门、翻书、消息提示）
- 音量控制接入设置面板

音频素材来源：先用免费素材（DOVA-SYNDROME、甘茶の音楽工房、Freesound 等）占位。原创音乐放最后。

### 7.2 UI 润色

- 文本框的视觉设计（半透明底 + 圆角 + 阴影）
- 字体选择（中文 VN 常用思源宋体/黑体）
- 选项按钮的 hover 动效
- 菜单的过渡动画
- 日期/节点日指示器（"节点日 3 · 深夜"）

### 7.3 额外功能（可选，挑着做）

- 对话历史回看（Backlog）
- 自动模式（自动推进对话）
- 已读跳过（已读文本可快进）
- CG 回想模式

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑7完成 | 有BGM/音效，UI看起来不再像"程序员界面" |

## 里程碑 8：打包发布——传统模式 v1.0

**目标**：把东西变成别人能下载/打开使用的软件。

### 8.1 Electron 打包（如果选 Web 技术栈）

```
npm install electron electron-builder
# 配置 package.json 的 build 字段
# npm run build → 输出 .exe / .dmg / .AppImage
```

主要处理：
- 窗口大小与全屏
- 本地文件读写权限（存档存储到 `app.getPath('userData')`）
- 图标

### 8.2 如果先发布 Web 版

更简单——静态文件部署到 Netlify/Vercel/GitHub Pages 即可。存档用 IndexedDB，完全离线可用。

### 8.3 测试 checklist

- [ ] 从头到尾通关一次（每个结局各一次）
- [ ] 存档/读档正常
- [ ] 设置面板各项生效
- [ ] 窗口模式/全屏切换正常
- [ ] 异常关闭后自动存档可恢复
- [ ] 找一个人试玩，观察他/她卡在哪里

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑8完成 | 传统模式 v1.0 发布，可下载/访问，可完整游玩 |

## 里程碑 9：AI 模式对接

**目标**：在主页面加上 AI 模式入口，对接 DeepSeek。

### 9.1 为什么放最后

传统模式是一个**完整的、独立可运行的游戏**。AI 模式是在它的基础上**替换对话生成层**。先把地基盖好、装修完，再开一扇新的门——这样你不会陷入"同时维护两个半成品"的困境。

### 9.2 步骤

1. 主页面改为双入口（传统模式 / AI 模式）
2. API 密钥配置页面
3. `LLMDriver` 接口 + DeepSeek 实现（参考 [[双模式架构与独立部署方案]]）
4. AI 模式对话管线——同一个剧本骨架，对话生成切换为 LLM
5. 两种模式的存档兼容

| 检查点 | 标准 |
|--------|------|
| ✅ 里程碑9完成 | 传统模式和AI模式在主页面并列可选，AI模式可正常对话 |

## 几个关键原则

### 1. 先跑通，再完善

每个功能的第一个版本只追求"能用"。typewriter 效果先用 `setInterval` 40行写完，不要上来就设计动画框架。**三个月后你会感谢现在的克制。**

### 2. 数据与逻辑分离

脚本是数据（JSON），引擎是逻辑（JS）。改剧本的时候不需要碰代码，改代码的时候不需要改剧本。这条线从一开始就划清楚。

### 3. 每次只做一件事

不要在加选择系统的时候顺便优化 UI。不要在写剧本的时候想"这个变量结构要不要重构"。一步一个 commit，出问题能精准回退。

### 4. 保持 demo-able

任何时候有人问"你在做什么"，你应该能打开一个页面给他看。这才是单人开发的节奏优势——你不需要等任何人，但你需要保持动力。
