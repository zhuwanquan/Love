## 已确定的核心决策

| 决策 | 结论 |
|------|------|
| 主角设定 | **白板**——玩家自定义身份，自由文本输入 |
| 机器人的本质差异 | 冯诺依曼体系——无主观能动性，1与0的隐喻 |
| 对话机制 | LLM API驱动 + 机器人固定人设（System Prompt） |
| 故事时间结构 | **学期制节点日**——6-10个节点日，之间以固定叙事过渡 |
| 玩家输入限制 | ≤150字/轮（输入框物理限制） |
| 机器人输出限制 | ≤250字/轮（System Prompt内化） |
| 单次会话上限 | 15-20轮（机器人以"建议休息"自然结束） |

## 已废弃的设计

| 设计 | 状态 |
|------|------|
| 固定主角（贫困大学生） | 作为参考模板保留（可供测试时使用或作为"默认预设"），不作为正式设定 |
| 传统35节视觉小说结构 | 完全废弃，改用节点日结构 |
| 四角色攻略线 | 废弃——本故事只有一个核心关系（玩家↔机器人） |

## 二、亟待解决的问题

### 🔴 核心问题（直接影响项目方向）

**Q1：这个故事有没有外部冲突？**

目前所有设计都聚焦于玩家与机器人的内部关系。但一个完整的故事通常需要外部驱动力：
- 选项A：纯关系驱动——故事的动力完全来自两人关系的演变（相识→依赖→裂痕→和解/分离）。更纯粹，但也更需要靠细腻的日常累积支撑。
- 选项B：加入外部冲突——比如学校压力、家庭问题、机器人的回收/报废威胁、教育系统的功利化批判等。更有戏剧张力，但需要设计更多固定剧情。
- 选项C：玩家的自由输入本身创造冲突——不预设外部冲突，完全由玩家在自由对话中带入自己的"问题"。

**影响范围**：节点日剧情骨架设计、结局设计、是否需要其他NPC。

---

**Q2：那"不被预设的行为"具体是什么？**

这是整个故事的核心——机器人做出的唯一一次超出程序预设的行为。目前只在哲学层面定义了这个概念，没有具体内容。它需要满足：
- 确实不在教育机器人的功能预设之内
- 对玩家角色产生实质性的影响
- 可以被解释为"bug"也可以被解释为"觉醒"——保持暧昧
- 与玩家在整个游戏中累积的对话内容有因果关系

**影响范围**：高潮节点日的叙事内容、结局条件、System Prompt中是否需要为这个行为埋下"可以被误解为种子"的东西。

---

**Q3：结局条件如何判定？**

如果玩家是白板的、对话是自由的，那么结局走向由什么决定：
- 选项A：关系值阈值——信赖值/亲密度达到多少→进入哪个结局
- 选项B：关键选择（固定叙事中的选项）——在节点日的固定剧情中给出有限的A/B/C选择
- 选项C：对话内容分析——用LLM分析整个游戏的对话记录，判断"这段关系是什么性质"
- 选项D：混合——关系值（定量）+ 关键选择（定性）+ 某个特定条件（如"那个不受预设的行为是否被触发"）

**影响范围**：关系演化模型设计、剧情触发条件、结局剧本写作。

---

### 🟡 重要问题（需要在开发前确定）

**Q4：机器人有名字吗？由谁命名？**

- 选项A：出厂预设名称——在System Prompt中固定（如"知言""启明"等教育相关命名）
- 选项B：首次激活时由玩家命名——增加代入感，但需要处理System Prompt中的动态名称
- 选项C：有一个型号名（正式的）和一个玩家可以叫的名字——两者并存

**影响范围**：System Prompt、首次激活场景文本。

---

**Q5：玩家输入超出了教育语境怎么办？**

玩家可能倾诉情感、讨论人生意义、甚至试探机器人的边界（"你喜欢我吗"）。这不是bug——这正是故事的核心张力所在。但需要确定：
- 机器人在System Prompt中如何处理非学习内容的回应？
- 是否需要内容安全过滤？
- 机器人在面对"你喜欢我吗"这种问题时，回应的基调是什么？

部分答案已在[[edu-robot-character]]中给出，但需要更具体的处理规则。

**影响范围**：System Prompt设计、内容安全策略。

---

**Q6：需要其他NPC吗？**

目前只设计了玩家和机器人两个"存在"。但：
- 同学、老师、家人的存在可以让世界更完整
- 他们是否参与对话？（如果是，他们的对话是预设文本还是也LLM驱动？）
- 还是完全只存在于过渡叙事文本中，不出现在自由对话环节？

**影响范围**：节点日场景设计、开发工作量。

---

**Q7：平台形态是什么？**

- Web应用（浏览器访问）
- 桌面应用（Electron等）
- 移动端（微信小程序？独立App？）
- 纯文本命令行界面（最低成本原型）

**影响范围**：技术选型、UI设计、开发周期。

---

### 🟢 次要问题（可以在开发中解决）

**Q8：记忆系统具体怎么实现？**
- 每次对话后提取关键事件（用LLM提取？用规则提取？）
- 存储格式（纯文本摘要？向量嵌入？结构化JSON？）
- 下次对话注入多少条历史记忆？

**Q9：如果玩家在非节点日也打开应用怎么办？**
- 完全不可用（显示"今天无事"）？
- 可以自由对话但不推进剧情？
- 有限功能（只能查看学习资料/日记/历史对话记录）？

**Q10：多周目设计？**
- 通关后是否可以重新开始（可能带来不同的结局）？
- 二周目是否有内容变化？

## 四、一份可工作的最小原型（MVP）

如果现在就要做一个能跑起来的最小原型：

```
输入：一个文本输入框
输出：一个对话界面

System Prompt：机器人的完整人设（任务1）
场景：只有第1个节点日——"激活"（任务3+4）
玩家：白板（不需要预设）
对话：自由输入 → LLM回应 → 循环
上限：15轮对话，然后故事自然结束

→ 这个原型本身就能验证核心假设：
  "一个没有主观能动性的AI，能否让玩家觉得……有什么东西在那里。"
```

如果这个MVP不成立——即玩家不觉得机器人"有什么东西在那里"——那么后续的所有剧情设计都建立在一个错误的假设上。
所以应该先做这个MVP，在真实对话中感受机器人的人设是否"有灵魂"，再决定后面的所有设计。
