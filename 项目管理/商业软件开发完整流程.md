# 商业软件开发完整流程

> 本文为单人/小团队独立游戏开发提供一套完整的流程框架——从最初的市场调研，到用户分析、产品定义、开发迭代、测试验证、发布运营。
>
> **前提**：单人开发者（或极小团队）——时间有限、资源有限。流程的设计原则是：**每一步都产出可验证的成果，每一步都为下一步提供方向，不做无法验证的"大而全"规划。**

---

```
  └→ 时代背景分析
  └→ 趋势判断（定性+定量）

  └→ 受众画像
  └→ 用户心理深描
  └→ 使用场景分析
  └→ 竞品分析
  └→ 需求优先级排序
  └→ 产出：我们为谁、解决什么、怎么做与别人不同？

阶段2：产品定义与MVP规划
  └→ 核心体验定义
  └→ 功能优先级（Must/Should/Nice）
  └→ MVP范围冻结
  └→ 技术选型

阶段3：原型与设计
  └→ 低保真原型（纸/线框图）
  └→ 核心流程验证
  └→ 高保真设计
  └→ 产出：可交互/可测试的原型

阶段4：内容生产（叙事类产品特有）
  └→ 剧本大纲 → 逐节点写作 → 修订
  └→ 素材清单与制作
  └→ 产出：完整剧本 + 素材

阶段5：开发实现
  └→ 核心引擎搭建
  └→ 功能模块开发
  └→ 内容集成
  └→ 产出：可运行的可交付物

阶段6：测试验证
  └→ 功能测试
  └→ 用户体验测试（内测）
  └→ 情感效果测试（叙事类特有）
  └→ 迭代修复
  └→ 产出：已验证的产品

阶段7：发布与运营
  └→ 上架准备
  └→ 推广传播
  └→ 用户反馈收集
  └→ 迭代更新
  └→ 产出：上线的产品 + 反馈循环

阶段8：复盘与迭代
  └→ 数据回顾
  └→ 用户反馈整合
  └→ 下一步决策（继续/转向/结束）
```

## 一、阶段0：市场调研与机会识别

### 1.1 核心问题

> **"有没有人在深夜打开手机，想找到一个会回应的人——但打开之后发现没有？"**

市场调研的目标是回答三个问题：
1. 需求存在吗？（定性 + 定量）
2. 现在是对的时间吗？（窗口判断）
3. 为什么是现在、为什么是你？（时机 + 独特性）

### 1.2 时代背景分析

不分析"当前市场有什么"——分析"当前时代缺什么"。

| 分析维度 | 方法 | 产出 |
|---------|------|------|
| 经济周期 | 宏观经济指标（GDP增速、失业率、房价收入比、消费信心指数）→ 判断当前处于经济周期的哪个阶段 | 时代坐标定位 |
| 社会心态 | 社交媒体热词分析（"内卷""躺平""emo""摆烂"）、搜索趋势（"治愈""陪伴""AI聊天"）、青年研究学术论文 | 核心情绪的命名 |
| 历史参照 | 对标经历过相似经济阶段的国家（日本1990s、韩国1997）→ 分析当时爆发了什么文化产品 | 需求强度的历史验证 |
| 技术条件 | 当前可用的技术栈——什么交互形式在本时代是"natively possible"的 | 产品形式的上限和下限 |

**本项目的实践**：[[中日对比与时代定位分析]]、[[韩国对照分析]]——时代背景分析已充分完成。

### 1.3 趋势判断

区分**长期趋势**（不可逆的、10年+）和**短期风口**（1-3年）。

| 趋势类型 | 本项目相关趋势 | 判断 |
|---------|-------------|------|
| 长期趋势 | 人口负增长→独居人口↑→孤独经济↑ | **确定的**。这是10-20年级别的需求增长 |
| 长期趋势 | AI能力持续提升→AI陪伴产品的体验不断升级 | **确定的**。意味着竞争会加剧——但也会扩大用户对"和AI聊天"的接受度 |
| 短期风口 | 2024-2026年"情绪经济"爆发，融资和市场关注度高 | **机会性的**。窗口在3-5年内。之后蓝海变红海 |
| 短期风口 | LLM成本下降→AI模式的边际成本持续降低 | **有利的**。BYOK模式越来越可行 |

### 1.4 机会窗口判断

> 日本galgame黄金期：泡沫破裂后2-9年（1992-1999）
> 韩国游戏产业爆发：IMF危机后1-5年（1998-2003）
> 中国情绪经济爆发：房地产崩盘后3-5年（2024-2029）

**窗口不会永远敞开。但窗口也不是"错过了就永远没有了"——日本的galgame衰退用了15年。中国的时间线被加速到2-3倍速，所以窗口可能是3-5年，而非10年。**

### 1.5 产出文档

- 时代背景与机会判断报告
- "做 vs 不做"决策（必须做出明确决定）

## 二、阶段1：用户分析与需求定义（详细展开）

### 2.1 用户分析的层次结构

```
层1：受众画像（Demographics）
  → 年龄、性别、身份、收入、设备、时间
  → 回答：谁？在哪里？有什么条件？

层2：心理深描（Psychographics）
  → 核心情绪、深层需求、消费心理、行为模式
  → 回答：他们内心的真实状态是什么？

层3：使用场景（Usage Scenarios）
  → 时间、空间、情境、触发条件
  → 回答：他们在什么状态下使用？

层4：需求层次（Needs Hierarchy）
  → 从表层到深层，哪些已被满足、哪些未被满足
  → 回答：我们的产品解决哪一层？

层5：竞品格局（Competitive Landscape）
  → 谁在解决同样的问题？他们做得好和不好的是什么？
  → 回答：我们和他们的差异在哪里、为什么用户选我们？
```

### 2.2 受众画像：从数据到画像

**步骤**：

1. **收集宏观数据** ——人口统计、网民结构、消费数据
2. **寻找"极端用户"数据** ——不是"平均用户"，而是"那些最需要你产品的人"的特征
3. **基于历史参照验证** ——日韩的时间序列数据帮助验证"谁是主要需求者"
4. **构建画像** ——将数据转换为具体的人物描述

**画像模板**（以本项目为例）：

```
姓名：（不需要真实姓名——用"22岁的他"）
年龄：24
身份：大学毕业两年，在二线城市做设计
居住：合租出租屋，月租1200
收入：8000/月，存不下钱
设备：一部手机（主力）+ 一台老旧笔记本
一天的结构：
  8:00 起床
  9:00-18:30 上班（有时加班到20:00）
  19:30 回到出租屋。外卖或楼下沙县
  20:00-23:00 刷B站/打游戏/发呆
  23:30 室友的房间灯关了。他的灯还亮着
  00:00 躺在床上。打开手机。想找人说点什么。
        但找谁呢。大学的朋友群已经三个月没人说话了。
  00:30 刷到一个B站视频。"我测试了一个AI聊天系统……"
        点进去。

核心情绪：不是难过。是一种持续的、安静的"没什么好期待的"。
最缺的：一个不需要解释自己为什么今天没有积极向上的人。
```

### 2.3 心理深描：从画像到动机

心理深描的核心问题是：**"他们为什么需要这个产品——不是他们自己说出来的原因，是他们自己可能都没意识到的原因。"**

**方法**：

| 方法 | 说明 | 适用性 |
|------|------|--------|
| **用户访谈** | 直接和目标用户交谈——但不要问"你需要什么"，问"你昨晚睡前在做什么"——行为>需求 | 最有效但也最耗时。MVP前3-5次深度访谈即可 |
| **竞品评论分析** | 阅读竞品的用户评论——不是看"他们喜欢什么"，是看"他们抱怨什么"和"他们得到的意外惊喜是什么" | 极低成本，极高信息量。本项目对《完蛋！》Steam评论的分析即属此类 |
| **社交媒体倾听** | 在贴吧、NGA、知乎、B站评论区观察目标用户自发讨论什么 | 低成本，中等信息量 |
| **行为数据分析** | 如果有早期产品，分析用户行为——不是他们"说"了什么，是他们"做"了什么 | 需要产品已上线或内测 |

**本项目的实践**：
- [[男性情感抑制与条件性价值内化]]——从童年社会化到成年情感真空的完整心理链条
- [[young-men-consumption-habits]]——《完蛋！》Steam评论情绪分析
- [[虚幻爱恋的理论基础]]——Winnicott、格式塔、神经科学多维度论证

### 2.4 使用场景分析

不要分析"理想使用场景"——分析**真实的生活片段**。

**场景分析模板**：

```
场景名：深夜·出租屋（最核心场景）
时间：23:00-01:00
地点：出租屋。一张床。手机屏幕是唯一的光。
情绪：疲惫、轻微虚无、不想刷短视频了但也不想睡
前置状态：刚关了B站。房间里只有空调的声音
动作：
  1. 解锁手机
  2. 看到RC-7的灰色图标（可能很久没开了）
  3. 犹豫了一下。点开
  4. 她说"你今天。"句号。停在那里
  5. 他打了几个字。删掉。又打。发了
  6. 她回复。3秒。句号。
  7. 继续聊。15分钟后。困了。关了手机
  8. 翻了个身。比平时快一点睡着了
后置状态：说了一些白天没说的话。不是"被治愈了"——是"说了"。
```

**场景分析的关键问题**：
- 在这个场景中，什么会阻止用户打开？（羞耻？太累？忘了产品存在？）
- 在这个场景中，什么会阻止用户继续？（对话质量差？被打断？觉得"没进展"？）
- 在这个场景后，用户会做什么？（睡？继续刷手机？截图分享？）

**本项目的实践**：[[分层受众精细化分析]]——四个主要子群体的不同使用场景。

### 2.5 需求优先级排序

**Kano模型简化版**：

| 需求类型 | 定义 | 本项目示例 |
|---------|------|-----------|
| **基本需求**（必须有——没有则用户愤怒） | 产品存在的底线 | 对话能打字、有回复、能存档 |
| **性能需求**（越多越好——线性关系） | 做得更好→满意度更高 | 对话长度、回复的贴切程度 |
| **兴奋需求**（惊喜——没有也无所谓，有了就爱上） | 超过预期的体验 | "她精确地引用了你两周前说的一句话"——用户没有在等这个 |
| **反向需求**（做了反而扣分） | 用户不需要但你以为需要的 | 社交排行榜、每日签到、氪金提示 |

**优先级原则**：MVP做全部基本需求 + 2-3个性能需求 + 1个兴奋需求。不碰任何反向需求。

### 2.6 竞品分析

见阶段0中引用的竞品数据文档。在用户分析阶段需要额外做的是：

**从用户视角分析竞品**：
- 用户为什么选择了竞品？（发现渠道？价格？朋友推荐？）
- 用户在竞品中得到了什么意外的东西？
- 用户在竞品中不满什么？
- 用户离开竞品的原因是什么？

**本项目的实践**：[[竞品数据对比分析]]——含《完蛋！》、日本galgame、AI陪伴、直播打赏的横向对比。

### 2.7 产出文档

- 用户画像（3-5个，覆盖核心群体的主要子类型）
- 心理深描报告
- 使用场景描述（5-10个真实场景片段）
- 需求Kano分类表
- 竞品分析报告
- 一句话定位：**"我们为[谁]解决[什么问题]，通过[什么方式]，与[竞品]不同的是[什么]"**

## 三、阶段2：产品定义与MVP规划

### 3.1 核心体验定义

> **核心体验 ≠ 产品功能列表**
> 核心体验 = 用户在使用产品时，内心深处发生的那个变化。

**定义核心体验的三步法**：

```
Step 1：命名体验
  "被精确地、恒定地对待"

Step 2：写出体验的故事（用户旅程）
  他从打开到关闭，内心发生了什么变化？
  → "打开时——只是想测试一下这个AI。
      关闭时——说了一些白天没说的话。
             不是'被治愈了'——是'说了'。"

Step 3：反推功能
  为了实现这个体验，产品必须具备什么？
  → 对话界面（载体）
  → 剧本（内容）
  → RC-7的回应逻辑（核心）
  → 存档系统（连续性）
  → 节点日结构（进度感）
```

### 3.2 功能优先级分类（MoSCoW法）

| 优先级 | 含义 | 本项目示例 |
|--------|------|-----------|
| **Must**（必须有） | MVP必须完成。没有这些就不是产品 | 对话界面、8个节点日剧本、选项系统、存档(至少1个槽)、结局判定 |
| **Should**（应该有） | 非常重要，但如果时间不够可以推迟到v1.1 | 打字机效果、5个存档槽、场景背景、自动存档 |
| **Could**（可以有） | 有更好，没有也可以。延迟到后续版本 | 语音消息TTS、叙事卡片配图、对话历史导出、自定义头像 |
| **Won't**（不做） | 明确不做——防止范围蔓延 | 社交功能、排行榜、每日签到、氪金、多角色选择、配音演员 |

### 3.3 MVP范围冻结

**原则**：
- MVP = 最小可验证产品。不是"最简单的版本"——是**"能验证核心假设的最简版本"**
- 核心假设："男性用户会在深夜打开这个对话界面，与一个被明确标记为程序的AI进行有深度结构的对话，并从这种'被精确对待'的体验中获得情感价值"
- 验证标准：内测用户是否自愿完成全部8个节点日？是否在结局体验到情感闭合？

**冻结清单**：
- [ ] 功能列表（Must项：是/否）
- [ ] 内容范围（8个节点日完整剧本）
- [ ] 技术方案（引擎架构+平台选择）
- [ ] 时间表（目标发布日期——可以浮动，但必须有）
- [ ] 不做的功能（明确列出，防止范围蔓延）

### 3.4 技术选型

| 考量维度 | 决策因素 |
|---------|---------|
| **平台** | 优先哪里？Web（零安装）/手机PWA/Steam/应用商店 |
| **技术栈** | 前端框架、后端需求（是否需要服务器？）、数据存储方案 |
| **AI集成** | LLM API的选择、计费模式、离线回退方案 |
| **单人维护性** | 技术复杂度必须=一个人能维护 |

**本项目的选择**：纯前端（HTML+CSS+JS）→ Web + PWA → 零服务器成本 → GitHub Pages部署。AI模式用BYOK。

## 四、阶段3：原型与设计

### 4.1 低保真原型

**目标**：验证核心交互流程。不需要好看——需要可测试。

**对于对话体叙事产品**：
- 低保真 = 一个真实的聊天界面，但回复是手写的（不是引擎生成的）
- 在纸上或笔记工具中模拟：玩家输入 → 切换到RC-7视角 → 写出回复 → 展示
- 测试：找2-3个人，让他们用这个"模拟器"进行一次对话。观察：
  - 他们说了什么？什么时候沉默？什么时候想退出？
  - 回复的时机对吗？长度对吗？内容对吗？

**这个阶段的成本**：极低。不需要写任何代码。只需要一份测试剧本的初稿和一个愿意花30分钟测试的人。

### 4.2 核心流程验证

**验证什么**：
- 用户能理解"这是聊天界面"吗？（不需要教学）
- 用户愿意连续发几轮消息吗？
- 3秒固定延迟 + 句号——对用户来说感觉对吗？还是觉得太慢/太快？
- 选项按钮（传统模式）的文本是否自然？（读起来像人会说的话吗？）

### 4.3 高保真设计

对话体产品的高保真设计相对简单——因为界面就是聊天框：
- 气泡样式、颜色、间距
- 字体大小和可读性
- 深色模式/浅色模式
- "正在输入…"动画
- 选项按钮的视觉位置

## 五、阶段4：内容生产（叙事类产品特有）

这是传统软件开发流程中没有的阶段——因为大多数软件不是内容驱动的。但对于叙事类游戏，这是**最长的单阶段**。

### 5.1 内容生产的流水线

```
大纲 → 分节点 → 逐节点写作 → 交叉审核 → 格式转换 → 引擎集成

Step 1: 大纲（1-2天）
  → 8个节点日的主题、情感弧线、关键事件
  → 4个结局的定义和触发条件
  → 变量系统设计（哪些flag影响结局？）

Step 2: 逐节点写作（每个节点日 1-2天 → 共8-16天）
  → 环境（叙事卡片文本）
  → 对话（15-20轮对话×2-3个选项路径）
  → 情感波动设计（每个节点日至少一个起伏）
  → 变量操作（哪些选项改变哪些flag）

Step 3: 交叉审核（2-3天）
  → 一致性检查：角色语调是否统一？情节是否连贯？时间线是否正确？
  → 变量检查：flag的加减是否合理？结局条件是否可达？
  → 情感检查：每个节点日的情感弧线是否有效？

Step 4: 格式转换（1-2天）
  → 将文学格式的剧本转为引擎可消费的数据格式（JSON/JS）
  → 验证格式——引擎能否正确解析？

Step 5: 引擎集成（1天）
  → 将数据文件接入引擎 → 逐节点日手动跑通
```

### 5.2 剧本评判标准

见 `最终内容/技术方案/剧本评判实用指南.md` 和 `/script-evaluator` skill。

### 5.3 素材清单

对于对话体产品，素材需求极低——这是单人开发的优势：

| 素材类型 | 必需？ | 制作方式 |
|---------|--------|---------|
| UI元素（气泡、按钮、头部栏） | 必需 | CSS绘制（零素材文件） |

## 六、阶段5：开发实现

### 6.1 单人开发的推荐流程

```
搭建骨架 → 核心循环 → 内容集成 → 打磨 → 测试

Week 1-2: 搭建骨架
  → UI框架（聊天界面）
  → 核心引擎（对话系统、存档系统）
  → 第一天（Day 1）的剧本数据 + 引擎集成
  → 跑通一个完整节点日 → 存档 → 读档 → 继续
  → 这是"全栈的1%"——验证技术方案可行

Week 3-4: 核心循环
  → 节点日跳转逻辑
  → 变量系统和结局判定
  → 选项分支的完整逻辑
  → 菜单系统（主菜单/暂停/设置）
  → 存档5槽位 + 自动存档
  → 跑通从第一天到结局的完整流程（用占位剧本）

Week 5-8: 内容集成
  → 逐节点日集成剧本数据
  → 每集成一个 → 跑通 → 修bug
  → 不在剧本写作期间碰引擎代码——反之亦然

Week 9-10: 打磨
  → 打字机效果
  → 过渡动画
  → 设置面板完整化
  → 调试面板（开发用）
  → 错误处理（存档损坏、数据加载失败等）
```

### 6.2 开发中的关键原则

| 原则 | 说明 |
|------|------|
| **先跑通，再完善** | 第一天就要有一个能"打开→对话→存档→读档→继续"的最小闭环。宁可用硬编码的手写对话去测试引擎，也不要等剧本写完才开始搭引擎 |
| **内容与代码分离** | 剧本是数据（JSON/JS文件），引擎是消费数据的程序。永远不要硬编码剧情内容到引擎里 |
| **每完成一个东西就存档** | 用git。每完成一个小功能就commit。个人开发不需要PR——但需要能回退 |
| **调试面板是必要的** | 单人开发没有测试团队——在引擎中内置调试面板（跳转节点/修改变量/清空存档），在测试时不要靠"从头打完整个游戏"来验证一个后期bug |

### 6.3 技术债务管理

对单人开发来说，技术债务的管理原则不同：

- **MVP阶段**：可以欠债。速度 > 代码质量
- **MVP验证后有用户了**：必须还债。稳定性 > 速度
- **永远不要欠的债**：存档系统——数据丢失会毁掉用户信任

## 七、阶段6：测试验证

### 7.1 测试层次

| 层次 | 谁 | 测什么 | 什么时候 |
|------|----|--------|---------|
| **开发自测** | 你自己 | 每写完一个节点日，跑通一遍。存档→读档→继续 | 持续进行 |
| **朋友测试** | 1-3个朋友，最好在目标受众内 | 能不能用？有没有卡住？有没有觉得无聊？有没有觉得"这东西有点意思"？ | MVP功能基本完成后 |
| **内测** | 5-15个目标用户 | **核心假设验证**：他们会自愿完成全部8天吗？在第几天关掉？在结局的感受是什么？ | 内容整合完成后 |
| **公开测试**（可选） | 更大范围 | Bug、性能、兼容性 | 正式发布前2-4周 |

### 7.2 叙事类产品特有的测试

传统软件测试关注：功能正确、无bug、性能达标。

叙事类产品还需要测试：

| 测试维度 | 方法 | 指标 |
|---------|------|------|
| **情感效果** | 内测用户每个节点日后填写一个极简问卷（1-2个问题） | 这个对话让你有什么感觉？在哪一句时感觉最强烈？ |
| **对话自然度** | 观察内测用户在选项中选择了什么——有没有某个选项几乎没人选？（说明这个选项的文本不够自然） | 选项选择分布 |
| **结局满意度** | 内测用户打到结局后的反馈 | "故事结束后——你觉得自己还会再想打开它吗？" |
| **技术情感干扰** | 是否有任何技术问题（卡住、bug、等待太久）打断了情感沉浸？ | Bug报告+用户反馈 |

### 7.3 内测的极简方案

**不需要专业的用户测试实验室。** 单人开发的内测方案：

1. 找5-8个人（朋友+朋友的朋友+社区），给一个链接
2. 不需要录屏、不需要全程观察（这是单人开发者没有资源做的事）
3. 需要的只是：**他们用完后回答3个问题**

```
问题1：你打到第几天了？如果没打完——在哪一天关掉的？为什么？
问题2：你在哪个时刻觉得"有点东西"？
问题3：你在哪个时刻觉得"不想继续了"？或者"不舒服"？
```

这三个问题提供的信息比100页详细问卷更有价值。

## 八、阶段7：发布与运营

### 7.1 上架准备清单

| 项目 | 说明 |
|------|------|
| **产品信息** | 名称、一句话描述、完整描述、标签、分类 |
| **视觉素材** | 图标（多尺寸）、截图（至少5张）、如果有视频更好 |
| **定价策略** | 免费/付费/免费+付费附加？ |
| **隐私说明** | 收集什么数据？为什么？存多久？ |
| **联系方式** | Bug反馈渠道（GitHub Issue/邮箱/社群） |
| **"给使用者的话"** | 见[[退出机制与伦理边界]]——首次启动引导中的伦理文本 |

### 7.2 发布平台决策

| 平台 | 优势 | 劣势 | 本项目适用性 |
|------|------|------|------------|
| **GitHub Pages** | 免费、零配置、版本控制 | 只有Web、国内访问可能有延迟 | ✅ 已在使用 |
| **Steam** | 高信任度、评测文化、自动触达目标受众 | 上架需要100美元费用、审核周期 | 推荐——免费游戏上架成本可回收 |
| **itch.io** | 免费、独立游戏社区、低门槛 | 国内用户少 | 可考虑——作为Steam的补充 |
| **应用商店（iOS/Android）** | 手机用户的天然发现渠道 | 审核严格、需要打包技术 | PWA可以绕过——但"添加到主屏幕"的用户教育成本高 |
| **微信小程序** | 触达中国用户的最短路径 | 审核、技术限制、需要企业资质 | 不适用于个人开发者 |

### 7.3 推广传播

详见[[男性获客路径与传播特性]]。关键原则：

- **零广告预算**。单人开发者没有推广预算——也不需要。产品本身是对话界面，对话截图就是最好的广告
- **种子用户**是关键——前50个用户决定口碑方向
- **推广的时间结构**：
  - 发布前2周：内测用户的自发传播
  - 发布日：B站1-2个视频上线 + 相关社区帖子
  - 发布后1-2周：Steam评测开始积累，口碑自然传播
  - 长期：产品在社区中的长尾讨论

### 7.4 用户反馈收集

| 渠道 | 收集什么 |
|------|---------|
| GitHub Issues | Bug报告、功能请求 |
| Steam评测 | 用户满意度、情感反馈 |
| 社区（NGA/贴吧/B站评论区） | 深度讨论、剧本分析、情感体验 |
| 直接反馈（邮箱等） | 个人化的反馈——最珍贵但也最难规模化 |

**如何处理反馈**：
- 反馈不是需求清单。一个用户说"我希望有更多结局"——不意味着必须做更多结局
- 关注**模式**而非**个案**：同一点被3+个用户提到 → 值得认真考虑
- 区分**噪音**（"我喜欢/不喜欢"）和**信号**（"我在第X天因为Y原因停止了"）

## 九、阶段8：复盘与迭代

### 9.1 核心问题

在发布后2-4周，回答以下问题：

| 问题 | 衡量方式 |
|------|---------|
| 核心假设被验证了吗？ | 内测/早期用户的反馈中，是否出现了预期的情感体验？ |
| 用户在什么时候流失？ | 如果发布了分析工具——看使用数据的断点 |
| 用户传播吗？ | 有没有自发的好评/截图分享/推荐？ |
| 哪里做得比预期好？ | 用户反馈中的"意外惊喜"——这些是后续版本可以强化的 |
| 哪里做得不如预期？ | 用户反馈中反复出现的批评 |
| 单人开发的瓶颈在哪里？ | 你最疲惫的部分——那是需要简化或放弃的地方 |

### 9.2 迭代决策树

```
          是否验证了核心假设？
          /                \
        是                  否
        │                   │
   用户反馈积极？         问题可能在哪里？
   /        \            ┌─────────────┐
  是         否          │ 需求不存在？   → 考虑转向
   │          │          │ 产品执行差？   → 找出具体问题→修复→再测
   │          │          │ 推广不到位？   → 扩大内测→获取更多反馈
   │     反馈哪里不对？   │ 时机不对？     → 等——或转型
继续  找出问题→修复→更新
迭代    │
        └→ v1.1 发布
```

### 9.3 单人开发者的节奏管理

这是传统开发流程中不会讨论——但对单人开发者至关重要的事：

- **发布后不要立即开始做下一件事。** 休息至少一周。你需要距离回看产品
- **发布后用户反馈会涌入**——先收集，不要急着每个都回应或修复
- **区分"必须修复"和"最好修复"**——发布后第一个月，只修bug，不加功能
- **为下一个版本设定明确的截止日期**——避免"永远在优化"

## 十一、总结：单人独立开发的核心原则

| 原则 | 说明 |
|------|------|
| **先验证需求，再写代码** | 本文的阶段0-1是免费的工作——不花一分钱、不写一行代码。但它决定你花半年写的代码有没有人用 |
| **MVP是能验证假设的最简版本** | 不是"最差版本"。是"刚好够验证你是不是在对的方向上" |
| **内容与代码分离** | 剧本是数据文件。永远不要在引擎里写死剧情 |
| **每步产出可验证** | 每个阶段结束都应该产出"可以给别人看/给别人试"的东西。不产出"只存在于你脑海中的计划" |
| **测试不是可选项** | 即使是单人开发。即使是朋友测试。3个人的反馈 > 0个人的反馈 |
| **发布不是终点** | 发布是"收集真正用户反馈"的开始。产品在发布后迭代——不是在发布前完美 |
| **照顾好你自己** | 一个人的团队意味着——你的身心健康是产品的单点故障源。给自己留休息时间 |
