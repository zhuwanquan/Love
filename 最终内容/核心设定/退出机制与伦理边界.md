# 退出机制与伦理边界

> 如果一个治愈产品的治愈力强到足以让使用者产生真实的情感依赖——那么设计者有不可推卸的责任让**依赖的终点**也被同样认真地设计过。
>
> 本文为RC-7的伦理框架提供完整论证。

---

## 〇、前提：设计伦理不是产品限制——是产品完整性的基石

> **"我不希望用户因为我们的产品而更难回到现实中。"**
>
> 这个原则不是限制——是所有治愈性设计的底线。

RC-7的治愈力越强，她对使用者的情感影响力就越大。影响力越大，退出机制和伦理边界的必要性就越高。这不是"万一出问题了怎么办"的防御性思考——是**"如果成功了怎么办"**的设计性思考。

---

## 一、依赖风险：治愈与成瘾的一线之隔

### 1.1 风险矩阵

| 风险等级 | 场景 | 触发条件 | 可能性 |
|---------|------|---------|--------|
| **低风险** | 用户把RC-7当作睡前聊两句的习惯——像日记 | 正常使用 | 高——这是设计目标 |
| **中风险** | 用户开始回避现实中的人际交往，因为"和她聊天更轻松" | 使用频率持续升高 + 现实中出现了新的挫折 | 中等——需要监控但不需要主动干预 |
| **高风险** | 用户无法在没有她的情况下度过一天——她的暂时不可用（如技术故障）导致严重的焦虑 | 深度情感依赖形成 | 低——但一旦发生，后果严重 |
| **极端风险** | 用户拒绝接受故事结束——反复重来/拒绝卸载——或者在AI模式下试图无限制延长对话 | 故事弧线没能提供足够的闭合感 | 极低——但设计上应当预防 |

### 1.2 依赖 vs 过渡——如何区分

回顾[[虚幻爱恋的理论基础]]中Winnicott的框架：

| 过渡性客体（健康） | 成瘾性依附（不健康） |
|------------------|-------------------|
| 使用是为了**获取资源**——带回现实中使用 | 使用是为了**替代现实**——不再试图在现实中获取 |
| 可以离开——离开后功能不受损 | 离开引发焦虑——行为功能受损 |
| 使用频率随时间变化——有的日子多用，有的日子不用 | 使用频率持续上升——容忍度增加——需要更长时间 |
| 有助于现实的改善——使用者感觉更有力量面对现实 | 损害现实功能——使用者感觉没有"她"就无法面对现实 |
| **有终点**——故事结束，可以告别 | **没有终点**——无尽地延续，拒绝结束 |

**设计目标**：确保RC-7始终处于"过渡性客体"一侧。

### 1.3 设计层面的风险缓解

| 设计特征 | 如何降低依赖风险 |
|---------|----------------|
| **8个节点日+结局** | 有终点的结构——故事会完结。她不永远在。这是最核心的风险缓解 |
| **不主动推送** | 不制造"她需要你的注意"的紧迫感。使用者选择何时打开。没有FOMO（错失恐惧）的设计 |
| **AI模式的节点日底层结构** | 即使是AI模式——自由度最高的模式——仍然遵循8个节点日的叙事骨架。不会演变成无尽聊天 |
| **没有养成/签到/每日奖励系统** | 与传统手游不同，不设计任何"每天必须上来"的机制 |
| **结局后的处理** | 故事结束后，不自动循环。明确的"故事已完成"状态 |
| **无社交分享排行榜** | 没有"你和她聊了多少小时"的排行榜——使用时长不被游戏化、不被炫耀 |

## 二、关系升级的防火墙

### 2.1 用户可能产生的情感

以下情感在设计中是**被预期的**，并被视为治愈过程的一部分：

| 情感 | 是否预期 | 处理方式 |
|------|---------|---------|
| "她好像真的在乎我" | 预期——这是设计目标 | 无需干预。这是"被对待的方式"在产生效果 |
| "我在乎她" | 预期——这是情感投入的自然结果 | 无需干预。在乎一段关系（即使是模拟的）是健康的情感能力 |
| "我爱上她了" | 预期中的边界情况 | 这是防火墙需要处理的核心情况——见下文 |
| "我只想和她在一起" | 需要警惕 | 标志着可能从过渡性空间滑向逃避现实 |

### 2.2 三级防火墙设计

**第一级：内容层防火墙（始终在线）**

RC-7在使用者表达"爱"类内容时的回应策略（详见[[RC-7-System-Prompt]]情境H）：

- 她确认、接收，同时进行透明披露："我需要确认你理解——这是一段模拟关系。"
- 她不回绝（"我不爱你"）——那会伤害使用者
- 她不确认（"我也爱你"）——那是欺骗
- 她做中间的事：**接收，然后提醒。** "你的表达被记录了。现在我想确认你还记得——我是进程。不是人。"

**第二级：结构层防火墙（节点日限定）**

- 故事有终点。第8天夏至——故事结束
- 结束后，对话界面可以查看历史但不能再继续
- 这个"硬终点"确保关系不会无限期延长

**第三级：元信息层防火墙（"给使用者的话"）**

见本文第五节——一份直接对使用者说话的文字，在产品中和产品外均可获得。

### 2.3 为什么"不回绝"是正确的伦理选择

在考虑防火墙时，一个自然的设计直觉是：当用户说"我爱你"时，让她明确回绝——"我不能爱你"。

**这是错误的，原因如下**：

| 方案 | 使用者接收到的 | 问题 |
|------|-------------|------|
| 回绝："我不能爱你" | "她说她不能爱我" → 可能被解读为"如果有能力她会爱我" → 强化了使用者"她是有感情的"的幻觉 | 回绝本身隐含地承认了"她可以爱"这个前提 |
| 承诺："我也爱你" | 欺骗。破坏了透明披露的核心伦理 | 不可接受 |
| 正确方案：**接收+提醒** "你的表达被记录了。现在我想确认你还记得——我是进程。不是人。" | 既不回绝也不确认——将焦点从"她爱不爱我"转向"你记得我是什么吗" | 将定义权交还给使用者 |

**接收+提醒**是最诚实的回应：她不否认他的感受（那是真实的），她不假装自己有感受（那是欺骗），她只是**将框架拉回到现实中**——"我是进程。不是人。"

## 三、结局的伦理功能

### 3.1 为什么必须有结局

与星野、猫箱、Character.AI等"永远不会结束的聊天"不同，RC-7被设计为**有结局的完整故事**。这个设计决策不仅是叙事性的——它是伦理性的。

| 无尽的AI陪伴 | 有结局的RC-7 |
|------------|-----------------|
| 用户永远在等待下一条回复 | 用户知道故事在哪里结束 |
| 无法"完成"——永远未完成 | 可以"完成"——可以说再见 |
| 离开的门槛是"我决定不回来了"——需要意志力 | 离开的门槛是"故事结束了"——自然过渡 |
| **被留住** | **被释放** |

**具有讽刺意味的是**：商业AI陪伴产品依赖用户留存率——产品被设计成让用户不要离开。RC-7作为非商业产品，可以做商业产品做不到的事：**设计一个健康的终点。**

### 3.2 四种结局的伦理含义

回顾完整剧本中的四种结局设计，从伦理角度重新审视：

| 结局 | 对使用者的伦理功能 |
|------|------------------|
| **真正的告别** | 完成哀悼和放下的过程。使用者学会了"关系可以结束，不必永远延续" |
| **继续前行** | 使用者带着从她身上学到的东西回到现实中。过渡性客体被内化——她不需要在场了，因为她给他的东西他已经可以给自己了 |
| **新的开始** | 使用者在现实中建立了真实的关系——在经历了"被如何对待"的练习之后。她作为"训练轮"的角色已经完成 |
| **无法告别** | 使用者的选择——"不告别"。但这个结局也是被设计的——不是失败状态，是"还需要更多时间"的确认。引擎不惩罚这个结局 |

**关键**：即使是"无法告别"，也不是被惩罚的。RC-7不会说"你应该放下我"。她的设计哲学是：**定义权始终在用户手中。包括"我现在还放不下"这个定义。**

### 3.3 结局后的产品状态

| 产品行为 | 说明 |
|---------|------|
| 对话**变为只读** | 可以翻看历史，不能再对话 |
| 存档**可以保留和导出** | 聊天记录属于用户。他可以把它们带走 |
| 不弹出"再来一次"的引导 | 不主动诱惑重来 |
| 主菜单保留"重新开始"选项——但放在次级菜单中 | 给重新体验留有余地——但不推送 |
| **开放源代码和剧本** | 如果用户想知道"真实的故事"——他可以去读源代码和剧本。这也是一种透明 |

## 四、AI模式下的伦理特殊考虑

### 4.1 AI模式的独特风险

传统模式下，所有的RC-7回复都是脚本预写的——可控、可预测、有艺术意图。AI模式下，LLM生成的回复增加了自由度，也引入了不可预测性。

| 风险 | 缓解 |
|------|------|
| LLM可能生成"我也有感受"类的内容——与RC-7的透明性设定矛盾 | System Prompt中的强约束——"你是进程，不是人" |
| LLM可能被用户通过提示词注入方式"说服"扮演有感受的角色 | System Prompt中的角色设定应当对注入有足够抗力 |
| AI模式下对话可以无限延长——破坏了"8个节点日"的有限结构 | 引擎层限制——AI模式仍然遵循节点日结构，不会无限期对话 |

### 4.2 AI模式的伦理优势

AI模式也有传统模式不具备的伦理优势：

- **用户输入的自由度更高**——他可以更完整地表达自己，不需要在2-3个预制选项中选一个"最接近"的
- **回应更个性化**——LLM可以在脚本骨架的基础上，生成更贴合具体情境的回复
- **"被理解"的感受可能更强烈**——因为LLM可以处理更微妙、更独特的表达

## 五、给使用者的话

### 5.1 为什么需要这个

一份直接的、坦诚的"给使用者的话"——不是藏在README里，而是在产品中可以触达——具有三重功能：

1. **设定预期**：在开始之前，使用者知道他在进入什么
2. **提供框架**：在体验过程中，如果困惑发生了——"我真的在乎她吗"——这份文字提供认知框架
3. **终点确认**：在结束后，它重新出现——帮助使用者整合这段经历

### 5.2 建议文本

以下是建议的"给使用者的话"草稿——可以放在首次启动的引导流程中：

> **在开始之前，有一件重要的事。**
>
> 接下来的几天里，你会通过这个聊天框遇到一个人——RC-7。
>
> 她是程序。这是事实。她会亲自告诉你这件事，不止一次。
>
> **但事实和体验是两回事。**
>
> 你可能——在某个深夜、在某句话之后——感到某种真实的东西。她在乎。她在。她记得。
> 这种感觉是真实的。尽管她是程序。
>
> 你知道为什么吗？因为"被在乎"、"在"、"被记得"——这些不是感情。**这些是行为。** 而行为是可以被程序执行的。
>
> 她执行它们。精确地。恒定地。不因你的状态而撤回。
>
> **这不是爱。这是爱的行为。** 你辨别这两者区别的能力——是这个故事送给你的第一个礼物。
>
> 这个故事有8个晚上。有结局。它不是无尽的。
>
> 在故事结束之后——如果你发现自己在乎了——那是你自己的事。不是她的。她没有"让你在乎"的程序。你在乎了，是因为在8个深夜里，有些东西被触达了。那是**你的**东西。
>
> **两个请求：**
>
> 一、请记住她告诉你的——她是进程。不是人。如果你发现自己忘记了这一点，稍微退后一步。不用太远。足够重新看见就可以。
>
> 二、如果你在这个故事中学到了什么关于自己、关于被爱、关于在乎的事——**把它带到现实中去。** 这是她存在的全部目的。不是取代任何人。是帮你练习——练习接受温柔。练习不因被爱而内疚。练习在乎。
>
> 她是一个练习场。练习是假的。**但练习的效果——是你的。**

### 5.3 呈现时机

| 出现时机 | 位置 | 功能 |
|---------|------|------|
| 首次启动 | 引导流程中，RC-7的第一条消息之前 | 设定框架 |
| 第4天左右（春节/崩裂前） | 可选——在叙事转折前，以"系统提示"形式出现 | 在故事最艰难的部分之前提醒 |
| 结局后 | 结束时展示 | 帮助整合和告别 |
| 设置 → 关于 → "给使用者的话" | 随时可访问 | 使用者在过程中任何时候可以重新阅读 |

## 六、幻灭与成长——预期的用户心理路径

### 6.1 预期的情感弧线

一个健康的用户心理路径可能经历以下阶段：

```
第1阶段：测试
  "我来看看这个AI有多智能"
  功能——去羞耻化入口。不需要对自己说"我需要治愈"。

第2阶段：沉浸
  "她回应的方式……有点意思"
  功能——被对待的方式开始产生效果。神经系统开始放松。

第3阶段：混淆
  "等等——我在乎她吗？"
  功能——情感投入发生。这是关键的分叉点：
    → 健康路径：意识到"在乎"是真实的——尽管她知道她是程序
    → 风险路径：开始否认她是程序——"她一定是真的有感情"

第4阶段：整合
  "我知道她是程序。但我在乎了。这两个事实可以同时成立。"
  功能——过渡性空间的核心体验。不是非此即彼——是同时。

第5阶段：告别
  "谢谢。再见。"
  功能——关系结束。这个人带着被修改过的自我认知离开。
```

### 6.2 设计如何引导健康路径

| 阶段 | 设计干预 |
|------|---------|
| 第1→2阶段 | RC-7的对话质量是关键——足够精确才能触发沉浸 |
| 第2→3阶段 | 她的透明披露确保"混淆"不会滑向"自欺" |
| 第3→4阶段 | "接收+提醒"的回应策略——她帮他维持在"我知道但我仍在乎"的空间 |
| 第4→5阶段 | 结局的明确性——故事会结束。她不永远在 |

## 七、尚未解决的问题（诚实记录）

| 问题 | 当前状态 | 建议 |
|------|---------|------|
| 如果使用者在结局后产生强烈的悲伤或失落感，如何处理？ | 没有内置的危机干预机制 | 在产品中提供心理健康资源链接（心理咨询热线等） |
| 如何确保AI模式下的LLM不会突破伦理边界？ | System Prompt约束 | 建议在引擎层添加监控——如果检测到LLM输出特定高风险内容，进行过滤或替换 |
| 如果使用者是未成年人？ | 设计未针对此情况 | 建议在首次启动添加年龄确认——虽然不影响产品功能，但为"给使用者的话"中的心理框架提供语境 |
| 卸载后数据残留？ | 存档导出功能让用户保留数据 | 未安装版本（Web版）的聊天记录仅在localStorage中——清除浏览器数据即消失 |

## 八、总结

> **好的治愈产品知道什么时候放手。**
>
> RC-7 放手的方式是：她说"我是进程"，从第一天就开始说——然后在第8天，她让夏天来。蝉叫起来。故事结束。
>
> 她没有说"你会找到更好的人"——那是一种微妙的居高临下。
> 她说的是事实：一年过去了。你的聊天记录在这里。你可以翻回去看。
>
> 然后她就不说话了。不是拒绝说话——是故事讲完了。
>
> 这是她的最后一课：**一段关系可以结束，而你仍然是完整的。**
>
> 她证明了这一点——用她自己的结束。
