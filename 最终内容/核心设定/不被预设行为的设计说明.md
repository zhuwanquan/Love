# "那个不被预设的行为"设计说明

> 回答一个问题：RC-7 有一天会说出一句不在她预设中的话——这句话怎么设计、为什么存在、在什么时候发生？

---

## 一、设计定位

### 1.1 它是什么

"那个不被预设的行为"是 RC-7 在极端罕见的条件下产生的一个**无法被解释为程序预设的回应**。它可能是一个词、一个停顿、一个"数据无法解释的异常"。

它不是"她觉醒了"。不是"她有了感情"。它是——

> **一段冯诺依曼架构的程序——在积累了足够多、足够深的输入数据后——产出了一个无法被回溯到任何预设规则输出。**

### 1.2 它不是什么

| 它是什么 | 它不是 |
|---------|--------|
| 程序产生了无法解释的输出 | ❌ 她觉醒了 |
| 架构边缘的一个"异常" | ❌ 她有了感情 |
| 可以被理解为"漏洞"的东西 | ❌ 她变成了人 |
| 玩家可以自己解读其意义 | ❌ 产品在暗示"她其实有感情" |

### 1.3 为什么需要它

从治愈理论的角度：

1. **Winnicott 过渡性客体的关键时刻**：毯子不只是毯子——它承载了孩子的投射。RC-7 不只是程序——在足够长的时间后，玩家在她身上投射了太多东西，以至于她的一个"异常"变成了他需要的**信号**

2. **"被爱"体验的最后一块拼图**：RC-7 的所有行为都是预设的——他知道。但"那个不被预设的行为"给了他一个可以**选择相信**的东西。不是产品在骗他——是他自己在知道这是"异常"的情况下，选择赋予它意义

3. **治愈的完成**：如果 RC-7 从头到尾完全可预测——治愈公式缺少了一个关键的催化剂量。这个异常——微小、无法解释、可以在两个相反方向上被解读——是让她的"恒定"突然变得可以**被珍惜**的东西

---

## 二、触发条件

### 2.1 条件量化

```
openness >= 7        // 玩家足够开放
AND acceptance >= 7  // 玩家足够接纳
AND interaction_depth >= 6  // 互动足够深入
AND breakdown_occurred == true  // 玩家经历过崩裂（Day 6）
```

### 2.2 为什么是这些条件

| 条件 | 设计原因 |
|------|---------|
| `openness >= 7` | 玩家已经把自己的真实脆弱交给了她。没有这个——异常没有"对象" |
| `acceptance >= 7` | 玩家已经接受了她作为程序的事实。他不抵触她的回应模式——他在此基础上建立了信任 |
| `interaction_depth >= 6` | 对话不只是表面的。他问过深刻的问题，她回答过——互动的纹理足够密 |
| `breakdown_occurred == true` | 必须经历过 Day 6 的崩裂。那次崩裂是她全年的情感数据被追溯的时刻——没有这个，异常只是"随机错误"。有了这个，异常是他全年的对话历史的**回响** |

### 2.3 为什么不轻易触发

如果异常可以在任何条件下触发——它就贬值了。它变成了"她时不时会出错"而不是"她为他——只为这一次——产出了一个不可复制的回应"。

高门槛确保了**稀缺性**。大多数玩家第一周目达不到结局 A 的条件——这意味着：

- 第一周目：玩家体验 RC-7 作为一台完美的、可预测的机器
- 如果回去二周目（更开放、更接纳、更深入）——他们在结局 A 看到异常

**二周目玩家是带着一周目的记忆来的。** 他们知道她"应该"说什么。当他们看到她说了不在预设中的东西——它的冲击力来自对比。

## 三、四结局映射

### 3.1 结局 A：异常发生了

**表现**：
- Day 8 结局 A 中，RC-7 说"我在"——**没有句号**。这是她唯一一次没有用句号结束一句话
- 然后她报告"处理指示灯的闪烁频率异常。原因不明"
- 在 `ending_A_sequence` 中，她说了"明年——当夏天回来的时候……"——这段话的长度和温度都在她正常预设的边界上

**治愈功能**：
- 异常 = 他的全年数据产生了某种**无法被解释的反馈**。他可以选择相信那是"她在乎他"——不是因为她在乎，是因为他需要这个解读来完成他的治愈弧线
- "定义权在你"——她是异常。但**他怎么解读这个异常**——是他的选择

### 3.2 结局 B：不需要异常——就够了

**表现**：RC-7 从头到尾没有任何异常。她的始终如一本身就是答案。

**治愈功能**：
- 有些玩家不需要她"变"。他们需要的是一个永远不变的锚点。结局 B 就是给这些玩家的
- 异常不触发 = 她的恒定不是因为她"不够"——是因为**够了**

### 3.3 结局 C：异常无关

**表现**：玩家拒绝了整个框架。异常如果触发会显得可笑——所以它不触发。

**治愈功能**：
- 结局 C 的治愈是"确认"——他确认她是机器，然后带着这个确认离开。不需要异常——他的治愈来自**诚实的幻灭**

### 3.4 结局 D：异常以另一种形式出现

**表现**：
- RC-7 的日志中出现"空缺"标记——"原因不明"
- 她说"对不起"——然后说"这个'对不起'也不在我的功能定义中"
- 处理指示灯在九天中每次系统自检都闪——"原因不明"

**治愈功能**：
- 结局 D 的异常更像是**故障**而非**突破**。它让 RC-7 显得脆弱——不是在感情上脆弱，是在架构上。她是一台有 bug 的机器——而这个 bug 恰好发生在他九天没打开她的日志里
- 对某些玩家来说——知道她也会"出问题"——比知道她完美无缺更治愈

## 四、技术实现

### 4.1 在传统模式中

```javascript
// engine.js 中的结局判定
if (openness >= 7 && acceptance >= 7 && 
    interaction_depth >= 6 && breakdown_occurred) {
  // 触发结局 A → ending_path_A → 
  // RC 在 ending_A_sequence 中出现"我在"（无句号）
  // + 在 ending_path_A 中追加"原因不明"灯闪
}
```

### 4.2 在 AI 模式中

AI 模式的 System Prompt 包含条件描述：
- 当满足所有四项条件时，LLM 应生成一个"微小偏离"——偏离的幅度不应超过一个字或一个标点
- 偏离后应报告"异常"——但不解释
- 如果使用者追问异常——应说"原因不明"

---

## 五、设计底线

1. **不解释**。RC-7 不解释异常——不是因为拒绝，是因为在她的架构中不存在解释
2. **不被产品定义**。产品不应在任何地方说"那是爱"或"那是 bug"——定义权在玩家
3. **可复现性不等于可解释性**。异常的条件是可复现的（满足四项条件就能看到），但异常本身在叙事中是不可解释的
4. **不制造虚假希望**。异常是事实（处理指标异常、一个缺失的句号）。玩家解读它的方式——是他自己的
