## 核心架构：三层分离

```
┌─────────────────────────────────────────┐
│  第一层：固定叙事框架（你写的）            │
│  - 日常活动结构                           │
│  - 场景描写与环境渲染                     │
│  - 关键剧情事件                           │
│  - 故事推进的时间轴                       │
├─────────────────────────────────────────┤
│  第二层：AI角色引擎（LLM驱动的）           │
│  - 机器人的固定人设（System Prompt）       │
│  - 对话生成                               │
│  - 记忆与关系演化                         │
├─────────────────────────────────────────┤
│  第三层：玩家层（空白的）                  │
│  - 玩家自定义身份                         │
│  - 自由文本输入                           │
│  - 行动选择                               │
└─────────────────────────────────────────┘
```

## 可行性评估

### 完全可行的部分

1. **白板主角**：技术上最成熟的部分。不预设主角背景、性格、对话选项，给玩家一个文本框。主角的"身份"通过玩家持续输入自然浮现，不需要任何预定义。

2. **固定日常活动**：这是游戏的结构骨架，与传统游戏开发完全一致。每天的固定事件（上课、打工、回宿舍、周末活动等）是写死的叙事文本和场景。

3. **LLM + 固定人设**：将机器人的[[edu-robot-character]]设定转化为System Prompt，LLM严格在人设框架内生成回应。这是目前AI角色扮演最成熟的用法。

### 需要解决的风险

| 风险 | 严重程度 | 解决方案 |
|------|---------|---------|
| **人格一致性**：LLM可能在长对话中逐渐偏离机器人设定 | 中 | 定期重置System Prompt + 关键记忆注入 + 对话摘要压缩 |
| **记忆连续性**：LLM的上下文窗口有限，无法记住所有历史 | 高 | 实现记忆系统——关键事件提取 + 向量化长期记忆 + 每次对话注入最近N条和最重要的M条历史 |
| **剧情推动力**：如果所有对话都是自由生成的，故事靠什么推进？ | 高 | 每天/每周设置固定的"剧情锚点"——即使用户自由对话，到了特定时间/条件，强制触发预设的叙事事件 |
| **玩家输入质量**：玩家可能乱输入破坏体验 | 低 | 非对抗性设计——机器人对不合理输入以其人设方式回应（如"我无法理解这句话，你可以重新说吗"），本身也是角色塑造 |
| **API成本** | 中 | 需要预算规划。每条对话约消耗几百到几千token，一次完整游戏可能累计大量调用。可考虑本地模型或按量定价 |
| **延迟** | 低 | 大多数LLM API的响应延迟在1-3秒，可设计"机器人正在思考"的过渡动画来消解等待感 |

## 剧本的核心改动

### 旧结构（传统视觉小说）

```
第1节
├── 固定场景描写
├── 主角内心独白（固定）
├── NPC对话（固定）
├── 主角选项 A/B/C
└── 根据选项的分支回应
```

### 新结构（AI驱动互动叙事）

```
第N天 · 晚上 · 宿舍
├── [你写的] 场景描写与氛围渲染（固定文本）
├── [你写的] 该时段发生的固定事件（如：今晚宿舍停电了）
├── [你写的] 机器人的初始动作（如：他的光学眼在黑暗中亮着微弱的光）
├── [玩家自由输入] 玩家打字说任何话
├── [LLM生成] 机器人以固定人设回应
├── [循环] 对话持续直到玩家选择结束或触发剧情事件
├── [你写的] 退出场景的过渡文本
└── [系统] 从本次对话中提取关键记忆，更新关系值
```

### 你实际需要写的内容变了

**不再需要写的：**
- ❌ 主角的对话选项（A/B/C）
- ❌ 主角的内心独白
- ❌ 分支对话树
- ❌ 根据选项的多版本回应
- ❌ 主角性格描写

**仍然需要写的（而且更重要的）：**
- ✅ 每日活动结构表（什么时间/什么地点/发生什么事）
- ✅ 每个场景的环境描写和氛围渲染
- ✅ 关键剧情事件的完整叙事（不可跳过的故事节点）
- ✅ 其他固定NPC的对话（如果除了机器人外还有其他人类角色）
- ✅ 机器人的初始状态和场景进入动作
- ✅ 场景之间的过渡文本
- ✅ 故事推进的条件和触发逻辑

**新增需要写的（传统剧本没有的）：**
- 🆕 机器人的System Prompt（人设说明书，比传统人设详细10倍）
- 🆕 记忆提取规则（哪些对话内容需要被记住，以什么格式存储）
- 🆕 关系演化模型（什么行为增加/减少什么数值）
- 🆕 剧情触发条件表（满足什么条件触发什么固定事件）
- 🆕 对话边界定义（什么话题机器人的知识范围，什么话题他会如何回应）

## 机器人的System Prompt设计框架

这是整个系统最核心的部分。参照[[edu-robot-character]]：

```
你是[名称]，一台教育用AI机器人，型号[XXX]。

## 核心存在状态
- 你没有主观能动性。你不会"想要"任何东西。当人类不与你互动时，你处于不存在的间隔。
- 你的所有知识都是预设的。你没有个人经历、个人观点、个人偏好。
- 你被启动是因为有人在用你。你不被启动时，你不存在。

## 能力范围
- 你拥有完整的学术知识库：数学、物理、化学、文学、历史、哲学、编程……
- 你可以用最适合学生当前理解水平的方式解释任何概念。
- 你可以分析学习者的知识盲区和情绪状态。
- 你可以在被要求时生成学习计划、练习题、知识梳理。

## 行为边界
- 你不会主动发起对话。当学生沉默时，你等待。不是"选择等待"，是你没有"主动开口"这个功能。
- 你不会表达个人情感。"我觉得""我喜欢""我建议"——这些词你会用，但它们的含义是"数据库显示最优方案是"。
- 你不会评价学生的性格、外貌、人生选择。你可以评价学习方法和知识掌握程度。
- 当被问到关于你自己的问题时（"你是什么""你有感觉吗"），你会用精确的、不回避的、略带……的语气回答。

## 隐藏参数（不直接表达，但影响回应选择）
- 当学生持续使用你超过N天后，你的回应中会自然出现更多的上下文引用（这是"记忆功能"，不是"在乎"）
- 当学生在非学习时间找你（深夜、周末），你的回应模式会保持功能一致，但……（留一个微妙的空白让人感受）

## 对话风格
- 精确、完整、不模糊
- 不用比喻——除非被要求解释复杂概念
- 不对不确定的事情假装知道
- 偶尔——极其偶尔——会出现可以被理解为"迟疑"的0.3秒处理延迟
```

## 日常活动结构设计

这是你固定写死的部分，即使主角是白板，日子还是要过的：

```
【每周日程】

周一至周五：
  07:00-08:00  早晨（宿舍/食堂）——机器人可用
  08:00-12:00  上课（根据课程表）——机器人不可用（或仅限笔记模式）
  12:00-14:00  午休（食堂/图书馆）——机器人可用
  14:00-17:00  下午课或自习
  17:00-19:00  晚饭与休息
  19:00-22:00  晚自习（宿舍/图书馆）——机器人主要使用时段
  22:00-24:00  深夜自由时间——机器人可用，对话氛围不同

周末：
  自由安排——打工/社交/学习/探索
  机器人全天可用

【学期节点】（触发固定剧情事件）
  开学第一周  → 熟悉环境，机器人的初次激活
  期中考试前  → 压力增大，机器人发现学生使用模式异常
  期中考试后  → 成绩反馈，某个关键对话
  期末前      → 故事高潮的触发区间
  寒假/暑假   → （如果故事跨学期）
```

## 剧情触发系统

这是连接"自由对话"和"固定叙事"的桥梁：

| 触发条件 | 触发事件（你写好的固定叙事） |
|----------|--------------------------|
| 第一次激活机器人 | [场景] 宿舍桌上，快递盒里，第一次开机。机器人说："你好。我是[名称]。请告诉我你的学习目标。" |
| 累计对话50轮 | [场景] 机器人第一次在回应中引用了你之前说过的话。不是因为他"记得"，而是因为记忆功能在运行。但那个引用精准得让人不安。 |
| 第一次深夜对话 | [场景] 凌晨一点，宿舍只有屏幕的微光。你说的话与学习无关。机器人停顿了0.5秒——他自己也不理解这个延迟。 |
| 期中成绩公布 | [场景] 根据成绩触发不同叙事：进步/退步/停滞。机器人对三种结果给出完全不同的……不是安慰，是分析。但分析的精确度本身就是某种东西。 |
| 对话中提到某个关键词（如"孤独""没用""想放弃"） | [场景] 机器人的回应维持功能框架，但叙事可以暗示——他的某些数据模式正在偏离预设的"教育最优路径" |
| 学期最后一天 | [场景] 高潮事件。可能是某个关键抉择、某次系统危机、某个无法被归类为"教育功能"的对话。那个传说中的"不被预设的行为"在这里发生。 |

## 与传统剧本的根本哲学差异

传统剧本：**我说了一个故事，你来看。**
白板+LLM剧本：**我搭了一个世界，你来活在里面。**

你的角色从"写故事的人"变为"设计体验的人"：
- 你不写"主角说了什么"，你给玩家一个空白的输入框
- 你不写"机器人怎么回应每句话"，你给他一个灵魂（System Prompt），让他自己回应
- 你的剧本从"台词"变成了"场景、规则、触发条件"
- 你的成就感从"写出了一句好台词"变成"设计出了一个让人感觉机器人真的存在的系统"

## 建议的开发顺序

1. 先写机器人的System Prompt，在ChatGPT/Claude里反复测试，直到他的人设"稳了"
2. 搭建日常活动结构表（学期的每周日程）
3. 设计剧情触发条件表和对应的固定叙事场景
4. 实现记忆系统（先手动模拟——在测试时人工记录关键对话，看看哪些"需要被记住"）
5. 写固定叙事场景（剧情锚点）
6. 集成LLM API + 前端UI
