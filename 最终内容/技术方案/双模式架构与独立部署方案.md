# 双模式架构与独立部署方案

> 基于需求 #1（双模式展示系统）的技术架构设计。
> 与 [[LLM互动架构方案]] 互补——本文聚焦双模式共存与部署架构。

---

## 一、总体架构原则

### 1.1 核心原则：完全单机

```
┌─────────────────────────────────────────────────┐
│                  用户设备                         │
│  ┌───────────────────────────────────────────┐  │
│  │           应用（单机运行）                   │  │
│  │  ┌─────────────┐  ┌───────────────────┐   │  │
│  │  │  传统模式    │  │     AI 模式        │   │  │
│  │  │  (纯本地)    │  │  (本地 + API调用)  │   │  │
│  │  └─────────────┘  └───────┬───────────┘   │  │
│  │                            │               │  │
│  │                     ┌──────▼──────────┐    │  │
│  │                     │  LLM 调用模块    │    │  │
│  │                     │  (可替换/MCP)    │    │  │
│  │                     └──────┬──────────┘    │  │
│  └────────────────────────────┼───────────────┘  │
│                                │                   │
│                      ┌─────────▼─────────┐        │
│                      │  DeepSeek API      │        │
│                      │  (外部服务)         │        │
│                      └───────────────────┘        │
└─────────────────────────────────────────────────┘
```

- **无服务端**：不设后端服务器，所有业务逻辑在用户设备本地运行
- **无用户系统**：不需要注册、登录、账号
- **无数据上传**：玩家对话记录、API 密钥等全部存储在本地
- **API 密钥由用户自行获取**：应用不内置任何 API 密钥，不代理任何 API 调用

### 1.2 与现有三层架构的关系

在 [[LLM互动架构方案]] 的三层分离基础上，第二层"AI角色引擎"根据模式不同有两种实现路径：

| 层级 | 传统模式 | AI 模式 |
|------|---------|--------|
| 第一层：固定叙事框架 | 同左（共享） | 同左（共享） |
| 第二层：AI角色引擎 | 预设对话文本 + 分支树 | DeepSeek API（System Prompt 驱动） |
| 第三层：玩家层 | 同左（共享） | 同左（共享） |

## 二、主页面双入口设计

### 2.1 页面结构

```
┌──────────────────────────────────────────┐
│                                          │
│           [游戏标题 / Logo]               │
│                                          │
│   ┌──────────────────────┐               │
│   │                      │               │
│   │   📖 传统模式         │               │
│   │   经典文字恋爱体验      │               │
│   │   无需任何配置          │               │
│   │                      │               │
│   │   [开始游戏]           │               │
│   └──────────────────────┘               │
│                                          │
│   ┌──────────────────────┐               │
│   │                      │               │
│   │   🤖 AI 模式          │               │
│   │   DeepSeek 智能驱动    │               │
│   │   需要 API 密钥        │               │
│   │                      │               │
│   │   [配置密钥并开始]      │               │
│   └──────────────────────┘               │
│                                          │
└──────────────────────────────────────────┘
```

### 2.2 交互流程

```
主页面
  ├── 点击「传统模式」
  │     └── 直接进入游戏（加载本地预设剧本数据）
  │
  └── 点击「AI 模式」
        ├── 首次使用：弹出密钥配置界面
        │     ├── 输入 DeepSeek API Key
        │     ├── [验证密钥] → 调用 DeepSeek API 简单测试
        │     ├── 验证成功 → 加密存储密钥到本地 → 进入游戏
        │     └── 验证失败 → 提示错误，允许重试
        │
        └── 已有密钥：直接进入游戏（密钥已存储在本地）
              └── 设置中可更换/删除密钥
```

### 2.3 密钥管理

- **存储位置**：用户设备本地（如 Electron 的 electron-store、浏览器的 localStorage/IndexedDB）
- **加密方式**：至少进行 base64 混淆 + 本地密钥加密（操作系统级密钥链优先）
- **验证方式**：调用 DeepSeek 的廉价/免费端点（如模型列表接口）验证密钥有效性
- **密钥更换**：在 AI 模式的设置界面中提供「更换密钥」和「删除密钥」选项
- **删除密钥后**：回退到主页面，AI 模式入口恢复为「配置密钥并开始」状态

## 三、LLM 调用模块：MCP 协议预留设计

### 3.1 设计目标

当前使用 DeepSeek API，但预留在未来替换为任意兼容 LLM 的能力。通过定义一个内部抽象的 LLM 调用接口，使上层业务逻辑与具体模型解耦。

### 3.2 模块接口抽象（伪代码）

```typescript
// LLM 驱动接口 —— 所有 LLM 实现必须满足此接口
interface LLMDriver {
  // 核心调用
  chat(messages: Message[], options?: ChatOptions): Promise<ChatResponse>;
  
  // 元信息
  readonly name: string;        // 驱动名称，如 "deepseek"、"openai"、"claude"
  readonly displayName: string; // 显示名称，如 "DeepSeek"
  
  // 能力查询
  validateKey(key: string): Promise<boolean>;
  getAvailableModels(): Promise<string[]>;
}

// 通用消息格式（OpenAI 兼容格式，业界最通用）
interface Message {
  role: 'system' | 'user' | 'assistant';
  content: string;
}

interface ChatOptions {
  model?: string;
  temperature?: number;
  maxTokens?: number;
  // 允许传递驱动特定参数
  extra?: Record<string, unknown>;
}

interface ChatResponse {
  content: string;
  finishReason: 'stop' | 'length' | 'error';
  usage?: {
    promptTokens: number;
    completionTokens: number;
  };
}
```

### 3.3 驱动注册与切换

```typescript
// 驱动注册表
class LLMDriverRegistry {
  private drivers: Map<string, LLMDriver> = new Map();
  
  register(driver: LLMDriver): void;
  get(name: string): LLMDriver | undefined;
  list(): LLMDriver[];
}

// 使用示例
const registry = new LLMDriverRegistry();
registry.register(new DeepSeekDriver());     // 默认驱动
// 未来可注册更多：
// registry.register(new OpenAIDriver());
// registry.register(new ClaudeDriver());
// registry.register(new LocalModelDriver());

// 用户配置中选择当前使用的驱动
const currentDriver = registry.get(userSettings.llmDriver) 
                    ?? registry.get('deepseek'); // 默认 fallback
```

### 3.4 MCP 协议未来对接点

当未来需要替换模型时，有两条路径：

**路径 A：直接实现 LLMDriver 接口**
- 新模型有官方 SDK → 实现一个新的 `LLMDriver` 类，注册到 Registry
- 无需改动上层代码

**路径 B：通过 MCP 协议**
- MCP (Model Context Protocol) 提供了标准化的 LLM 工具调用和上下文管理
- 如果未来模型支持 MCP，可以将 `LLMDriver` 作为 MCP Client 的实现
- MCP 的标准化接口天然适合"替换模型"的场景
- 在驱动层预留 MCP 适配器：

```typescript
// MCP 适配器 —— 将 MCP 兼容的模型包装为 LLMDriver
class MCPDriverAdapter implements LLMDriver {
  constructor(private mcpEndpoint: string, private mcpConfig: MCPConfig) {}
  
  async chat(messages: Message[], options?: ChatOptions): Promise<ChatResponse> {
    // 通过 MCP 协议调用模型
    // MCP 标准定义了统一的 chat/completion 端点
  }
}
```

### 3.5 预留清单

| 预留项 | 说明 | 当前状态 |
|--------|------|---------|
| `LLMDriver` 接口 | 所有 LLM 调用的抽象接口 | 设计中，待实现 |
| `LLMDriverRegistry` | 驱动注册与切换机制 | 设计中，待实现 |
| 用户设置中的 `llmDriver` 字段 | 持久化用户选择的驱动 | 待实现 |
| MCP 适配器 | 为 MCP 兼容模型预留的适配层 | 预留接口，暂不实现 |
| DeepSeek 驱动 | 首个具体实现 | 由作者后续自行实现 |

## 四、两种模式的数据流对比

### 传统模式数据流
```
玩家输入
  → 本地剧本引擎（匹配预设分支）
  → 返回对应预设文本
  → 显示
全程无网络请求
```

### AI 模式数据流
```
玩家输入
  → 拼接 System Prompt + 记忆上下文 + 玩家输入
  → LLMDriver.chat() → DeepSeek API
  → 返回 AI 生成文本
  → 显示
  → （可选）记忆提取 → 本地存储
仅在对话生成环节有网络请求
```

## 五、安全考虑

| 风险 | 应对 |
|------|------|
| API 密钥泄露 | 本地加密存储，不通过网络传输给任何第三方服务器 |
| AI 生成内容不可控 | System Prompt 内化行为边界；如 DeepSeek 提供内容过滤 API 则启用 |
| 玩家输入敏感信息 | 数据全在本地，不上传；在应用内提示玩家不要输入个人隐私信息 |
| API 费用滥用 | 密钥由用户自行提供，费用由用户自己的 DeepSeek 账户承担；可在应用内显示每次调用的 token 消耗估算 |
